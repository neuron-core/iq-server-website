Where the savings come from

Fewer servers.

3.4 to 9 times less CPU per event than general-purpose servers, and up to 35 times more events on the same two CPUs.

Fewer components.

No Redis cluster to relay events between nodes, no database for history, no disk to provision, monitor and back up.

Fewer wasted LLM generations.

Users whose connection dropped get the rest of the answer instead of retrying it, and every avoided retry is a full generation nobody pays for again.

Less code to own.

Reconnection, ordering, end-of-answer signals and slow-client handling are done.

Lower latency, better product.

Tokens reach the screen in milliseconds, not seconds, even at peak.

IQ looks up customers in the store you already run (PostgreSQL, MySQL, Redis, or an internal API) and caches what it reads. No separate customer database to sync, no extra service to operate.

Usage you can meter.

Each customer’s live counters (active answers, connected viewers, memory in use) are available per app, ready to feed dashboards, alerts and usage-based billing.

Isolation you can sell.

One customer’s spike cannot take capacity from another. A customer at its limit gets a clear “limit reached” answer for its own new streams, while every other customer keeps streaming.

Few moving parts to operate.

No broker, no database, no disk, no cross-node message bus in the data path. A server that keeps nothing on disk upgrades with a rolling restart, and grows with the CPUs you give it.

Fits regulated and sovereign clouds.

Signed images, SBOMs, provenance records, non-root execution and air-gapped installation fit the compliance reviews of providers serving finance, healthcare and the public sector. Answer content is never logged or written to disk.

Many isolated applications

Many apps that don’t trust each other, on the same servers.

IQ can host the streams of many independent applications, belonging to different teams or different customers, on the same servers, safely.

Separate credentials per app.

Each app signs its own tokens with its own secret. One app can never publish to, or read, another’s streams.

No noisy neighbours.

Cap each app’s concurrent answers and memory. An app that hits its limit loses only its own new streams. Every other app keeps streaming as if nothing happened.

Limits per app, per plan.

Concurrent answers, memory, answer size, maximum duration, viewers per answer, timeouts. Change them in your own database and they apply within a minute, without a restart.

Plug into the customer database you already have.

A JSON file, Redis, PostgreSQL or MySQL, or your own internal service through a small connector. A slow or failing store never takes streaming down: IQ caches answers and keeps serving known apps through a store outage.

Per-app monitoring without sharing secrets.

Each app gets a monitoring key that reads only its own live counters (active answers, viewers, memory) and can never publish or read a stream.

Protected by design.

Fake credentials are rejected before they cost a lookup, and floods of unknown app keys are rate-limited, so a public endpoint stays standing.

Single-tenant

One company, one or more apps.

Run IQ next to your application and give it your app’s credentials. Your backend signs a short-lived token for each answer: one to publish, one to watch. The browser gets only the token to watch, and only for that answer.

FAQ

Questions providers ask first.

Can one IQ deployment serve many customers?

Yes. Multi-tenancy is built in: separate credentials, separate limits and separate counters for every app, with no customer able to read, write or crowd out another’s streams.

Can I run it in my own cloud?

Yes. IQ is a single Docker image for amd64 and arm64, signed and verifiable, that runs anywhere Docker runs, air-gapped networks included.

Does IQ store our customers’ conversations?

No. IQ keeps an answer in memory only while it is being generated, so a browser that reconnects can resume. Once the answer ends and the browsers watching it have read it, IQ drops it. It never writes content to disk and never logs it.

What happens if IQ restarts mid-answer?

Answers in flight on that process are lost, and browsers are told so explicitly, so the app can load the result from its backend. Planned restarts drain gracefully: running answers get time to finish first.
